## 3. 效果分析

### 3.1 为什么 MSGC RSS 大幅降低？

MSGC（MarkSweep GC）相比 CopyGC 的核心架构差异导致了 RSS 的显著降低：

#### ① 原地回收 vs 拷贝翻倍

| 特性 | CopyGC | MSGC |
|------|--------|------|
| 回收方式 | 将存活对象**拷贝到新空间**，旧空间整体释放 | **原地标记死亡对象**，sweep 后释放 region |
| 内存峰值 | 需要 **2× 存活集大小**的空间（旧空间 + 新空间同时存在） | 仅需 **1× 存活集 + 少量碎片** |
| RSS 影响 | 每次 GC 时 RSS 飙升（分配新 to-space），GC 后才释放 from-space | RSS 保持平稳，不存在翻倍峰值 |

**这是 RSS 降低的最主要因素。** 以 case3 为例：~500MB 存活集在 CopyGC 下每次 GC 需要 ~1GB 空间（from + to），而 MSGC 仅需 ~500MB + sweep 开销。

#### ② 增量式内存归还

MSGC 的后台 sweep + scavenge 机制持续将空闲 region 归还给操作系统：

- **后台 Sweep**：GC 标记完成后，后台线程逐步扫描 region，将死亡对象的 region 标记为空闲
- **Scavenge**：当空闲 region 池超过阈值（seed3 中仅 4 个 region = 8MB），立即通过 `madvise(MADV_DONTNEED)` 归还物理页
- **Inline Reclaim**：分配路径中内联回收，分配即清扫，进一步减少滞留

CopyGC 的内存归还是"批量式"的——整个 from-space 在拷贝完成后一次性释放，期间 RSS 持续处于高位。

#### ③ 精细的空闲池控制

seed3 将空闲 region 池下限从默认 32（64MB）压缩到 2（4MB），消除了 CopyGC 为保证 to-space 充裕而必须预留的大量空闲内存。

### 3.2 为什么 case3 效果最显著（RSS -73%）？

case3 的工作负载特征完美匹配 MSGC 的优势：

1. **大存活集（~500MB）**：CopyGC 每次拷贝 500MB 存活对象需要额外 500MB to-space，峰值接近 1GB。MSGC 原地标记不需要额外空间
2. **高临时对象比例（50%）**：MSGC 的 sweep 可以快速回收死亡 region，空闲 region 被 scavenge 立即归还
3. **长运行时间（~120s）**：MSGC 的后台 sweep 有充足时间完成增量回收，RSS 持续维持在低位
4. **CPU 几乎无代价（+0.1%）**：因为 MSGC 单次 GC 耗时极短（0.67ms 均值），高频率 GC 的 CPU 开销被分摊到了长运行时间中

### 3.3 为什么 case5 CPU 偏高（+37%）？

case5 包含大量大对象（64KB~8MB），导致：

1. **Mark 阶段扫描量大**：大对象内部的指针/数据需要更多扫描时间
2. **GC 次数激增（31→344）**：seed3 的低阈值（4MB）在大对象场景下触发更频繁的 GC
3. **Sweep 大 region 耗时**：单个大对象可能占据整个 region，sweep 需要逐个处理

但这一 CPU 代价换来了 **75.8% 的 RSS 峰值降低**（316MB → 76MB），在内存受限场景下是合理的权衡。

### 3.4 单次 GC 停顿为什么更低？

| 特性 | CopyGC | MSGC |
|------|--------|------|
| STW 工作 | 扫描根集 + **拷贝全部存活对象** | 扫描根集 + 标记启动（**不拷贝**） |
| 并发阶段 | 无 | 并发标记 + 后台 sweep |
| 停顿时间 | 与存活集大小成正比 | 与根集大小成正比（标记并发化） |

MSGC 将最耗时的操作（标记扫描、sweep）移到了并发阶段，STW 停顿仅包含根集枚举和标记启动/终止，因此：
- case1 单次 GC：5.70ms → 2.68ms（**-53%**）
- case3 单次 GC：2.96ms → 0.67ms（**-77%**）

### 3.5 代价总结

| 代价 | case1 | case3 | case5 |
|------|-------|-------|-------|
| 墙钟时间 | +23% | **-3%** | +18% |
| CPU 均值 | +18% | +0.1% | +37% |
| GC 总耗时 | +90% | +76% | +958% |

代价主要体现在：
- **CPU 开销增加**：并发标记和后台 sweep 消耗额外 CPU
- **GC 总累计时间增加**：虽然单次 GC 更快，但次数大幅增加
- **大对象场景代价较高**（case5）：大对象的 mark/sweep 开销未被并发化摊薄

---

## 4. 关键结论

### MSGC 的核心优势

1. **RSS 内存大幅降低**：三个用例 RSS 均值降幅 54%~73%，峰值降幅 42%~76%
2. **GC 停顿更短**：单次 GC 耗时降低 5%~77%，90% 以上 GC 在 1ms 内完成
3. **长运行场景近零代价**：case3（120s）运行时间反而略减 3%，CPU 几乎无增加

### MSGC 的适用场景

| 场景 | 推荐程度 | 原因 |
|------|---------|------|
| 内存受限环境 | ★★★★★ | RSS 降幅 50%+，同样的物理内存可支持更多实例 |
| 延迟敏感服务 | ★★★★★ | 单次 GC 停顿更短，尾延迟更低 |
| 长运行服务 | ★★★★★ | 后台 sweep 有充足时间完成回收，代价可忽略 |
| 大对象密集 | ★★★☆☆ | RSS 仍有优势，但 CPU 代价较高 |
| 极短命程序 | ★★☆☆☆ | GC 累计开销尚未摊薄到足够运行时间 |

### 与 CopyGC 的本质差异

```
CopyGC:   分配 → 满了 → STW 拷贝存活到新空间 → 释放旧空间
          ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
          RSS 锯齿：低 → 高（分配 to-space）→ 低（释放 from-space）

MSGC:     分配 → 阈值触发 → 并发标记 → 后台 sweep → scavenge 归还
          ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
          RSS 平稳：持续维持在存活集 + 少量缓冲
```
