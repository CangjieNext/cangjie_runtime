# MSGC 用例执行环境避坑与规避指南

> 记录日期：2026-08-28  
> 依据：本轮检查的 macOS 历史执行结果；本文只归纳非用例逻辑本身导致的执行问题。

## 1. 适用范围与结果分类

本文服务于 MSGC SDK 的 Runtime、标准库和编译器用例执行。它不替代用例失败分析：先排除环境、构建和框架问题，剩余可稳定复现的编译/运行异常才进入功能缺陷队列。

建议统一记录以下结果，避免把“未真正执行”误报为 FAIL：

| 结果 | 含义 | 是否作为用例失败 |
| --- | --- | --- |
| PASS | 已以 MSGC 成功编译并运行，期望匹配 | 是（成功） |
| FAIL | 命令有效、环境已核验，但编译/运行/比对失败 | 是 |
| UNSUPPORTED | 当前平台、SDK 包或测试框架能力不具备，无有效执行命令 | 否 |
| ENV-ERROR | 环境、动态库、第三方工具、网络或资源不足导致未完成 | 否 |
| SKIP | 已知不适合常规回归的专项用例，留待专门配置执行 | 否 |

凡是没有生成有效的编译或运行命令，尤其是框架显示 `no valid command`，必须标为 `UNSUPPORTED`，不能计入 FAIL。

## 2. 执行前基线检查

### 2.1 固定 SDK 三件套

每个测试批次都在报告中写明以下来源：

- compiler：SDK 内的 `bin/cjc`（Windows 为 `bin/cjc.exe`）；
- runtime：同一 SDK 内与目标平台匹配的 `runtime/lib/<platform>/libcangjie-runtime.*`；
- stdlib/stdx：同一 SDK 的动态标准库目录和 `dynamic/stdx`。

MSGC 编译必须显式加入 `--gc-mode marksweep`。替换过 SDK runtime 后，所有 `.cj` 用例必须重新编译，不能复用旧二进制，否则二进制和 runtime 的 GC 初始化数据、符号引用可能不匹配。

### 2.2 动态 stdx 目录必须精确

历史 macOS 执行最初把 stdx 指向 `.../dynamic` 的父目录，导致运行时找不到 stdx 包。应指向实际包目录：

```text
<sdk>/<platform>/dynamic/stdx
```

在 Windows MSGC SDK 中，对应目录为：

```text
<sdk>/windows_x86_64_cjnative/dynamic/stdx
```

设置 `CANGJIE_STDX_PATH` 为该目录，并把 SDK runtime、`bin`、工具目录和 `cjpm` 放入 `PATH`。执行前用一个最小 stdx import 用例做编译与运行探针。

### 2.3 每套 SDK 使用隔离环境

macOS 多 SDK 对比时，连续 `source envsetup.sh` 会遗留旧 `DYLD_LIBRARY_PATH`，后续程序可能静默加载另一套 runtime，使性能或功能结果失真。每套 SDK 应使用干净子 shell；并以动态加载日志确认实际加载的 `libcangjie-runtime.dylib` 路径。

Windows 不使用 `DYLD_LIBRARY_PATH`，但同样不能混用多个 SDK 的 `PATH`、`CANGJIE_HOME` 或 `CANGJIE_STDX_PATH`。每个批次启动独立 PowerShell/`cmd`，只注入当前 MSGC SDK 的路径，并先执行 `where cjc` 和 DLL 加载探针。

### 2.4 先做 SDK 包预检

历史报告中缺少 `stdx.syntax`、`stdx.chir`、`std.log`、`std.ffi.python`、`std.reflect`、`stdx.plugin.manager` 等包。这表示 SDK 打包能力不完整或用例依赖未安装，不应归因于 Runtime。

规避方法是：在全量调度前扫描用例 import 与 SDK 包目录；缺失包对应的用例组标 `UNSUPPORTED` 并单列记录。补齐 SDK 后再取消排除，不要把临时排除固化成 runtime 结论。

## 3. 编译、链接与依赖问题

### 3.1 测试框架未自动带 MSGC 模式

普通 cjnative 配置常只配置 `cjc`，并不自动加入 MSGC 模式。必须通过框架配置覆盖或统一编译包装，把实际编译器命令固定为：

```text
cjc --gc-mode marksweep -j1
```

批量运行前先保留一份框架最终展开的实际命令。若某些用例直接调用 `cjc` 而绕过 `%compiler`，应记录为“未使用 MSGC 模式的框架路径”，先修正该路径或单独跳过，不能将结果混入 MSGC 回归统计。

### 3.2 测试框架宏或宿主工具缺失

`%link-python`、`%enableSwitchOpt` 一类框架宏未定义时，命令会以原始占位符执行；macOS 报告中的 `dos2unix` 缺失也属于宿主工具缺失。这些都不是用例逻辑失败。

处理原则：

- 对可补齐的依赖，先在执行机安装工具或在测试配置中定义等价宏；
- 对仅适用于其他平台的宏，按平台排除并记录；
- 保留原始错误和最终展开命令，分类为 `ENV-ERROR` 或 `UNSUPPORTED`。

### 3.3 静态/动态库不能混合链接

历史 TLS/HTTP 用例在同一进程混用静态与动态 OpenSSL/libcrypto，触发不安全的加载或符号冲突。规避方式是让单个进程只使用一种 OpenSSL 链接模型；未修复前，将相关 FFI/TLS 用例放到独立进程、独立环境执行，并从常规 GC 回归中隔离。

### 3.4 平台链接参数与库依赖

历史 macOS 静态链路需要 `-lc++`，并发现公共链接参数遗漏 `-lstdx.effect`。这两类错误表现为链接失败，但与 GC 功能无关。

处理方法：

- 使用目标平台对应的 C++ 运行库；macOS 为 `-lc++`，Windows 不能照搬，应遵循 Windows 工具链的 C++ 运行库规则；
- 对依赖 effect 的用例，确保链接配置已包含 `stdx.effect`；
- 先用单例用例验证全局链接参数，再启动整组 API 用例。

## 4. 运行与调度问题

### 4.1 Finalizer 与 CJThread 交互需专项执行

历史执行中，带 `finalizer`/`gc-helper` 的用例曾出现 SIGSEGV 或依赖 sleep 的时序不稳定。此类用例同时覆盖 GC 回收、析构、协程/线程调度，不能作为普通高并发回归的环境健康判据。

常规回归仅保留简单 finalizer smoke；涉及 CJThread、强制 GC、异步析构或 gc-helper 的用例统一放入专项组，以固定并发度、明确超时和诊断日志运行。专项失败记录为 FAIL 前，先核验 GC 模式、runtime 来源和可重复性。

### 4.2 内存压力和内部多进程

大对象、内存压力和嵌套多进程用例会受机器内存、外层并发与进程配额影响，可能表现为 OOM、超时或子进程启动失败。运行这些组时：

- 降低外层并发（推荐先 `-j1`）；
- 按用例需要设置 `cjHeapSize`，并记录实际值；
- 不与全量回归混跑；
- 若宿主资源不足，标记 `ENV-ERROR`，等待专用资源复测。

### 4.3 网络、端口和时间相关用例

网络测试易受 DNS、代理、防火墙、端口占用和时钟精度影响。应串行或低并发运行，给出合理的单例超时；仅在确认测试依赖可达后才把超时判为用例失败。可重试的临时网络失败单列为环境异常，保留首次和重试日志。

### 4.4 输出比较被诊断文本污染

部分严格比较用例会把编译器/运行时调试信息写到 stderr，从而造成文本差异。应关闭不属于用例契约的调试开关或在框架中明确分离 stdout、stderr；不能通过全局过滤 stderr 掩盖真实诊断变化。历史报告中的 CopyGC/MSGC 诊断差异也应作为模式差异单列。

## 5. 平台与编译器接口差异

### 5.1 不复制 macOS 专用命令到 Windows

`-lc++`、`xcrun`、`DYLD_LIBRARY_PATH`、`DYLD_PRINT_LIBRARIES` 等是 macOS 链路或加载器设置。Windows 批次应使用当前 SDK 的 DLL 搜索路径和 Windows 工具链参数；平台命令照抄会产生伪失败。

### 5.2 编译器/SDK 接口必须先探测

历史编译器用例曾受 `--common-part-chir` 不受支持、`[cj-compiler-rebuilt]` 诊断文本混入影响。处理方式不是永久排除：先对 SDK 做版本和选项预检；若接口已恢复，重新启用相关测试；若未恢复，归为 `UNSUPPORTED`，附上 `cjc --help`、版本信息和最小复现命令。

### 5.3 使用准确的动态库加载检查

macOS 用加载器日志确认 `libcangjie-runtime.dylib` 来源；Windows 应在隔离 PATH 下运行最小可执行文件，必要时用 Process Monitor、`dumpbin /dependents` 或 loader 日志确认实际加载的 `libcangjie-runtime.dll`。没有确认 runtime 来源的结果不进入 SDK 对比结论。

## 6. 推荐执行流程

将测试拆为两个层级，既避免环境噪声污染主统计，也不遗漏专项覆盖：

1. **常规回归**：Runtime LLT → Runtime HLT → 标准库 LLT/HLT → 编译器 LLT/HLT。使用固定 MSGC 编译参数、正确动态 stdx、SDK 包预检和常规并发度。遇错只记录路径、命令、退出码和分类，不在本轮逐例分析。
2. **专项回归**：finalizer/CJThread、内存压力、嵌套多进程、网络/TLS/FFI、需额外包或宿主工具的用例。为每一组设置独立并发度、堆大小、超时、依赖和重试策略。

每个阶段结束立即写入结果文件：SDK 三件套来源、实际框架命令、开始/结束时间、通过/失败/跳过数量、失败路径、`UNSUPPORTED` 与 `ENV-ERROR` 清单，以及原始 JSON/日志目录。只在退出码和结果文件均已落地后，才宣称阶段完成。

## 7. 快速检查清单

开始一个批次前逐项确认：

- [ ] `cjc` 来自目标 MSGC SDK，且编译命令包含 `--gc-mode marksweep`。
- [ ] runtime、stdlib、stdx 与 compiler 来自同一 SDK；`CANGJIE_STDX_PATH` 指到 `dynamic/stdx`。
- [ ] 本批次环境不残留另一套 SDK 的动态库路径。
- [ ] runtime 替换后已重新编译本批次所有 `.cj` 用例。
- [ ] 目标 SDK 所需包、框架宏和宿主工具已预检；缺失项有 `UNSUPPORTED` 清单。
- [ ] 链接模型和平台库参数正确，TLS/FFI 没有混用静态/动态 OpenSSL。
- [ ] finalizer、压力、网络和内部多进程用例已从常规回归拆出。
- [ ] 框架记录了最终执行命令、退出码、日志与结果文件位置。
- [ ] 对 FAIL 已排除 `no valid command`、加载错误、资源/网络不足等环境原因。
