# C2R 回栈方案通俗说明

这份文档用比较直白的方式说明：  
为什么要给 `C2R` 补一套完整的回栈机制，这套机制准备怎么做，做完以后实际效果是什么。

## 1. 先说问题是什么

先看一条常见调用链：

- `cj -> runtime -> cj`

意思是：

1. 仓颉代码先通过 `C2RStub` 调到了 runtime 侧辅助函数/调用链
2. runtime 在执行过程中，又回调到了另一段仓颉代码

这时候线程栈里通常会有三段：

- 外层仓颉栈
- 中间 runtime 栈
- 内层仓颉栈

问题在于，中间这段 runtime 栈不一定总能被稳定识别出来。  
如果某些平台上 runtime 地址范围识别失败，系统就可能把这段 runtime 栈误当成仓颉栈去解析，接着去读不该读的元数据，最后 crash。

所以这个方案的核心目标很简单：

- 不要让系统去硬解析中间那串普通 runtime 帧
- 让回栈时把这整段 `C2RStub` 调用的 runtime 调用链压缩成一个稳定边界

## 2. 这个方案想做成什么效果

理想效果不是把 runtime 里的每一层都精确展开，而是把它当成一个“边界区段”。

也就是说，原来可能看到的是：

- `inner cj -> runtime frame 1 -> runtime frame 2 -> runtime frame 3 -> outer cj`

改完以后，回栈更希望看到的是：

- `inner cj -> N2C boundary -> C2R boundary -> outer cj`

这里的意思是：

- 内层仓颉代码照常展开
- 中间普通 runtime 帧不再一层层展开
- 只保留两个边界
  - `N2C`：runtime 回调仓颉的边界
  - `C2R`：仓颉进入 runtime 的边界

这样做以后，系统就不需要先识别出中间每一层 runtime 普通帧，才能继续回栈。

## 3. 为什么现有 C2R 还不够

现在的 `C2RStub` 更像一个“调用包装器”：

- 先保存一些寄存器
- 再通过 `C2RStub` 调用 runtime 侧辅助函数
- 最后返回

它适合做寄存器保护，也适合给 GC 提供一个稳定边界。  
但它还缺少一套像 `N2C` 那样的“记住 caller 在哪里”的机制。

所以一旦线程已经落在 `C2RStub` 调用的 runtime 侧调用链里面，再去打印栈、做异常栈、做 signal 栈时，系统还是得从当前普通 runtime 帧开始往回走。  
这就又回到了“必须先正确识别 runtime 普通帧”的问题上。

## 4. 方案的核心想法

可以把这个方案理解成两句话：

1. 进入 `C2RStub` 时，先把“我是从哪里来的”记下来
2. 在线程位于 `C2RStub` 调用链内部回栈时，不再从中间普通 runtime 帧开始，而是直接从 `C2R` 边界开始

为了做到这件事，需要补两块能力。

### 4.1 在 `C2RStub` 里加一个 slot

这个 slot 可以理解成一张小纸条，里面记三件事：

- caller 的 `pc`
- caller 的 `fa`
- caller 的 `status`

也就是：

- 上一个边界是谁
- 它的栈帧在哪里
- 它当前是可靠状态还是风险状态

这样将来回栈走到 `C2RStub` 时，就知道该跳回哪里。

### 4.2 进入 `C2RStub` 调用链时改一下 TLS 顶层上下文

这一步更关键。

如果只是把信息写进 `C2RStub` 的 slot，但不改线程当前的顶层回栈上下文，那么线程在 `C2RStub` 调用链内部触发回栈时，入口还是会落在普通 runtime 帧上。

所以需要在进入 `C2RStub` 后，顺手把线程 TLS 里的顶层 `UnwindContext` 切换成：

- 当前就站在 `C2R` 边界上

这样以后不管是在 helper 里打印栈，还是做异常栈，还是做 signal 栈，系统都可以直接从 `C2R` 边界开始，而不用先去认中间那一串普通 runtime 帧。

## 5. 用一条调用链来看它怎么工作

假设现在是这条链：

- `outer cj -> C2R -> runtime 调用链 -> N2C -> inner cj`

回栈时可以这样理解。

### 第一步：外层仓颉进入 runtime

进入 `C2RStub` 时：

- 先把当前顶层上下文保存到 `C2R` slot
- 再把 TLS 顶层上下文改成“现在在 `C2R` 边界”

这时系统已经记住了：

- 外层 caller 在哪
- 当前 runtime 区段的入口边界在哪

### 第二步：runtime 再回调到仓颉

如果这一步走的是 `N2CStub`，那么 `N2CStub` 保存 caller 信息时，看到的“当前顶层上下文”已经不是普通 runtime 帧了，而是前面设置好的 `C2R` 边界。

这意味着：

- `N2C` 记住的 caller，不会掉进这段 runtime 调用链内部
- 而是会直接指向外层 `C2R` 边界

### 第三步：内层仓颉开始回栈

这一段没有特殊之处，按普通 managed 栈展开即可。

### 第四步：回栈跨过 N2C

回栈走到 `N2CStub` 时，直接从 `N2C` slot 里恢复 caller。  
恢复出来的 caller 不是这段 runtime 调用链里的普通帧，而是外层 `C2R` 边界。

所以中间那串 runtime 普通帧就被跳过去了。

### 第五步：回栈跨过 C2R

接下来再从 `C2RStub` 回到外层仓颉 caller。

最终效果就是：

- 内层仓颉栈保留
- 中间 runtime 普通帧被压缩
- 外层仓颉栈继续保留

## 6. 这个方案的直接价值

这个方案最重要的价值不是“栈更漂亮”，而是“系统更稳”。

具体说有三点。

### 6.1 避免把 runtime 普通帧误判成仓颉帧

既然中间普通 runtime 帧不再参与主要回栈路径，就不容易再被当成 managed 帧去解仓颉元数据。

### 6.2 `cj -> runtime -> cj` 这种嵌套场景能闭环

这类场景最怕边界上下文串不起来。  
补齐 `C2R` 机制以后，`C2R` 和 `N2C` 两层边界能自然接起来，回栈链条是闭合的。

### 6.3 GC / EH 设计更容易保持一致

GC 和异常处理本来就更依赖边界帧，而不是依赖中间普通 runtime 帧。  
所以把这段 `C2RStub` 调用链压缩成边界，和现有方向并不冲突。

## 7. 它的代价和限制

这套方案不是没有代价。

### 7.1 中间 runtime 调用细节会变少

做完以后，调试栈会更短。  
如果有人想看这段 runtime 调用链内部每一层怎么调，信息会比以前少。

### 7.2 依赖边界路径稳定

这个方案对 `cj -> runtime -> cj` 的处理，依赖 runtime 回调仓颉时确实经过 `N2CStub`。  
如果某条路径绕开了标准边界，这套压缩逻辑就不能自动成立。

### 7.3 会改到 stub 布局和回栈协议

这不是一个只改一两个函数的小补丁。  
它会涉及：

- `C2RStub` 栈布局
- TLS 顶层上下文切换
- unwind 逻辑
- GC / EH / signal / 栈打印 等相关路径

所以工作量和回归面都不小。

## 8. 一句话总结

这套方案本质上是在做一件事：

- 把“仓颉进入 runtime，再从 runtime 回到仓颉”这段复杂过程，压缩成两个可靠边界，而不是依赖中间普通 runtime 帧逐层识别

它不是为了保留最完整的 runtime 内部栈，而是为了：

- 回栈更稳
- 嵌套边界更清晰
- 避免 runtime 帧误判成仓颉帧后引发 crash
