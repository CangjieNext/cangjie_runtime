# 实践二：AI 辅助特性开发设计说明

## 1. 背景与目标

当前 [MSGC_RESULT/doc/AI实践/web/index.html](/Users/lipeisheng/code/cangjie/cangjie/cangjie_runtime_MSGC/runtime/MSGC_RESULT/doc/AI实践/web/index.html) 中“实践二：AI 辅助特性开发”已经具备基本内容，但核心对比区仍然偏文字化，无法直观传达 CopyGC 与 CMSGC 在分配路径、回收路径和碎片处理方式上的根本差异。

本次改造的目标有三点：

1. 把“实践二”提升为整页最重的内容区块，让它承担“技术路线差异讲清楚”的任务。
2. 用工程架构图而不是文字流程卡来表达 CopyGC 与 CMSGC 的机制差异。
3. 保持中间态受众友好度，即图本身保持工程味，旁边或下方用少量中文说明做翻译。

目标受众不是纯 runtime 工程师，也不是完全非技术观众，而是“有一定技术背景、但不一定熟悉 GC 内部实现”的评审、分享听众和跨团队同学。

## 2. 范围与非目标

本次改造的范围如下：

1. 重做“实践二：AI 辅助特性开发”整段的结构、文案和样式。
2. 把现有 `MSGC` 对外展示文案统一调整为 `CMSGC`，但保留少量代码级、实现级语义，例如日志风格中的 `MS-GC`。
3. 为新的双架构图区补充必要的 HTML 结构和 CSS 样式。
4. 保留现有 benchmark 图表与结果数字，但重新安排它们在“实践二”中的位置与权重。

本次明确不做的事情：

1. 不对整页其余章节做同等级别的重构。
2. 不更换现有 benchmark 图片资源和数据来源。
3. 不把实践二改成纯论文式长文，只做适合分享页的高密度展示。

## 3. 内容结构

“实践二”完整区块采用四层结构，从上到下形成“问题背景 -> 机制对比 -> 数据验证 -> 结论收口”的闭环。

### 3.1 引子层

引子层保留当前已有的两个信息块，但会压缩为更短、更聚焦的形式：

1. 为什么要预研 CMSGC：
   说明在 taibai 等更偏服务端的场景里，高并发、大内存、长时间运行会更快暴露 CopyGC 的边界。
2. AI 参与方式：
   说明工程师负责路线判断，AI 负责方案细化、代码展开、用例构造和实验收敛。

这一层的作用是“带观众进入问题”，而不是承担主要讲解任务，因此视觉上权重低于核心架构图区。

### 3.2 核心架构图区

核心架构图区是整个“实践二”的视觉中心，采用左右并列的双架构板：

1. 左侧：CopyGC
2. 右侧：CMSGC

每个架构板再拆成两层：

1. 上半部分画分配路径
2. 下半部分画回收或 sweep / reclaim 路径

这两张图不再以项目符号和短句为主，而是用 `region` 方框、`slot` 栅格、链表、箭头、碎片空隙、整块涂色等视觉元素直接表达机制。

### 3.3 证据层

架构图区下方保留已有 benchmark 图表，但重新定义其角色：

1. 它们不再是本节主角，而是“机制解释之后的证据”。
2. 小内存场景结论仍然保留，说明 CopyGC 在小堆、小存活集下依然有竞争力。
3. 大内存高并发场景结论继续保留，说明 CMSGC 在 RSS 与单次 GC 时间方面的优势更明显。

### 3.4 收口层

最底部保留一条简洁的结论收口，强调：

1. 这轮预研不是简单替代 CopyGC。
2. 其价值在于为后续更偏大内存、高并发、长跑场景的项目准备可验证的备选方案。
3. AI 的价值体现在缩短方案形成、实验验证和结论沉淀的闭环时间。

## 4. 架构图区设计

### 4.1 图形语言统一原则

CopyGC 与 CMSGC 两张图必须使用统一的工程图语言，避免一边像示意图、一边像文字卡片。统一原则如下：

1. 用实体框表示 `region`、`slot group`、`heap region`、中央池节点等对象。
2. 用箭头表示对象流动、region 流转、分配界限推进或回收路径。
3. 用颜色状态表达对象是否存活、region 是否已满、是否未清扫、是否空闲。
4. 文字只做标签和最少量翻译，不承担主要机制说明。

### 4.2 CopyGC 图的最终表达

CopyGC 图采用单 `P0` 视角，突出“线性 bump 分配 + 复制聚集回收”。

分配侧要求：

1. 只保留一个 `P0`，避免多 P 分散注意力。
2. `tlRegion` 用一个长条 region 表示：
   - 左侧整块绿色表示已分配区域
   - 中间一条竖线表示当前 `allocPtr` / 分配界限
   - 右侧白色表示尚未分配区域
3. 堆用一个大的外框表示整体 Heap。
4. Heap 内部用很多等高不同宽的小框表示 region 分布：
   - 以 `64K` 为主
   - 插入两个 `128K`
   - 插入少量 `5K`、`20K`
   - 中间零星夹杂碎片空隙
5. Heap 旁边配一棵笛卡尔树，用 7 个大小不同的无文字方格节点和连线表示“大块 region 在堆首”的管理特征。

回收侧要求：

1. 左边画多个碎片化 region，每个 region 内再拆成小框。
2. 小框内部用竖向绿色线条表示存活对象：
   - 线条粗细和密度不同，表示存活对象大小和多少不同
   - 白色块表示不可复用空间或已死亡对象留下的空位
3. 中间用 `copy ->` 箭头表示搬迁。
4. 右边目标 region 用整块绿色表示存活对象被重新聚集。
5. 被清空的 region 保持白色，表示可释放回堆。

### 4.3 CMSGC 图的最终表达

CMSGC 图也采用单 `P0` 视角，突出“多 size-class region + slot 分配 + 中央池 + concurrent sweep”。

分配侧要求：

1. `P0` 下面同时出现多个不同 size-class 的 region。
2. `16B / 32B / 64B` 的 slot 必须直接体现尺寸差：
   - `16B` slot 更密、更小
   - `32B` slot 更大
   - `64B` slot 最大
3. slot 的颜色状态：
   - 绿色表示已占用
   - 白色表示空闲

中央池要求：

1. 用 `36 buckets` 的结构表达中央池，不需要把 36 个都展开，但要明确这是 bucket 化管理。
2. 每个 bucket 下画 4 条链表：
   - `partialSwept`
   - `fullSwept`
   - `partialUnswept`
   - `fullUnswept`
3. 链表上的 region 节点本身也要带状态，而不是只写名称：
   - `partial`：region 框内绿白混合，表示未满
   - `full`：region 框内全绿，表示已满
   - `unswept`：region 框内黄褐色，表示尚未清扫
4. region 节点之间用链表箭头连接，体现中央池不是抽象集合，而是实际链式组织。

回收侧要求：

1. 左边画 mutator lazy sweep 与 background sweep 两个参与者。
2. 中间用 `sweep ->`、`reclaim ->` 箭头表示路径。
3. 右边分别画：
   - 回到 swept lists 的 region
   - 完全 empty 后回到 heap 的 region

### 4.4 说明区安排

每张架构图都保留一小段“看图说明”，但严格控制篇幅，目标是翻译而不是重复。

例如：

1. CopyGC 说明区强调“通过搬迁存活对象来聚集内存”。
2. CMSGC 说明区强调“对象不搬迁，而是 region 在不同状态链表之间流转并被复用”。

## 5. 文案策略

### 5.1 名称调整原则

对外叙述统一使用 `CMSGC`，原因是当前分享内容强调的是并发 Mark-Sweep 路线，而不是泛指某个内部实现简称。

需要保留原有实现术语的场景包括：

1. 代码或日志原样引用，例如 `MS-GC`
2. 实现细节文档标题或函数名
3. 与现有 benchmark 数据、日志特征、实现模块强绑定的地方

### 5.2 正文叙事顺序

正文遵循下面的顺序：

1. 先说“为什么要做”
2. 再说“CopyGC 与 CMSGC 在机制上根本不同”
3. 再说“这种机制差异在 benchmark 里体现成什么结果”
4. 最后说“AI 在这轮特性预研里起到了什么作用”

这样可以避免直接堆图或直接堆数据，保证听众先建立问题感，再理解机制，再接受结果。

### 5.3 AI 角色表述

“AI 辅助特性开发”一节里的 AI 角色应该保持准确，不夸大成“AI 设计了 GC”。

推荐表述是：

1. 工程师负责技术路线、边界判断和实验口径。
2. AI 负责方案细化、代码展开、测试用例构造、对比分析与文档沉淀。
3. AI 的核心价值不是替代判断，而是加速“想法 -> 原型 -> 验证 -> 结论”的周期。

## 6. 视觉与版式要求

### 6.1 区块权重

“实践二”必须比当前版本明显加高、加重，成为整页里视觉上最有存在感的章节之一。允许这一节的高度明显高于“实践一”或“实践三”。

### 6.2 布局关系

推荐版式如下：

1. 顶部：引子层双卡片
2. 中部：双架构板并列，占主要高度
3. 中下：差异总结带
4. 下部：benchmark 图表与数据结论
5. 底部：结论收口

### 6.3 图文比例

这一节以图为主、文为辅：

1. 核心架构图区至少占本节 50% 以上的视觉面积。
2. 文案尽量变成短句和标签。
3. 长段说明只出现在引子层和证据层。

### 6.4 差异总结带

差异总结带保留，但只收敛 4 个点：

1. 分配热路径
2. 对象是否移动
3. 碎片处理方式
4. 更适合的场景

这个总结带的作用是帮助听众在看完复杂图之后快速回忆核心差异。

### 6.5 图表位置

当前已有的小内存和大内存 benchmark 图表继续保留在核心图区下方，不删除，但降权处理：

1. 先讲机制，再给图表
2. 图表作为“结果证据”，不抢核心图区的主导地位
